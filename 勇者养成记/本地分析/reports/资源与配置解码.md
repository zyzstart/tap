## 2. resbin 头部：545 / 545 校验通过

所有 resbin TextAsset 使用 20 字节候选头布局：

| 字节偏移 | 类型 | 含义 / 约束 |
|---:|---|---|
| 0 | BE uint32 | tag，当前样本为 `0x2def` |
| 4 | BE uint32 | 整个文件长度，包含头部 |
| 8 | BE uint32 | version，按原值保留，不假设统一业务版本含义 |
| 12 | BE uint32 | record count |
| 16 | BE uint32 | 载荷反相 CRC32 |
| 20… | bytes | 记录载荷 |

计算公式是 `zlib.crc32(data[20:]) ^ 0xffffffff`，**不是直接将 zlib CRC32 与头字段比较**。545 份均满足 magic、全文件长度和反相 CRC；这证明数据边界和该校验模型一致，但不证明字段语义。

逐项结果、原始 Bundle/path ID/字节哈希见 [配置索引](<../derived/config-decoded/resbin-index.json>)；统计见 [配置汇总](<../derived/config-decoded/resbin-summary.json>)。

## 3. 如何选择 schema，为什么有的表不解码

声明来源是 [ARM64 dump](<../derived/il2cpp/arm64-v8a/dump.cs>) 中 `ResDef` 与 `BattleCore` 的类、字段对象偏移及 `unpack` RVA。这里的 `ProtoBase.ProtoBaseStruct` 和 `ProtoBase.BProtoBaseStruct` 是**接口**，不是基类，也不能据名称认定采用 Google protobuf。

选择规则：

1. Bundle 名含 `_resbin_fp_` 优先 `BattleCore`，其余优先 `ResDef`。
2. 优先命名空间没有精确类名时，只有支持命名空间内恰好一个同名类才作为后备。
3. 字段声明若不能完整识别则不采用；数组、嵌套对象、枚举及未知类型不猜测。
4. 同名后备表为避免覆盖 FP 版本，非 FP 输出可使用 `__nonfp` 后缀。每张表保留 `schema_selection`。

首轮结果（历史基线）：

| 状态 | 数量 | 处理 |
|---|---:|---|
| 静态模型解码通过 | 280 | 201 张 ResDef、79 张 BattleCore，共 108,533 条记录 |
| 数组/嵌套/枚举等不支持 | 174 | 保留原字节、头部与原因 |
| 无无歧义命名空间/同名 schema | 71 | 不强行配类 |
| 候选 schema 与载荷边界/字符串/尾部不符 | 20 | 拒绝解码，不补零、不忽略尾部、不输出伪造数据 |
| 合计 | 545 | 头部全部通过，剩余 265 张未输出记录数据 |

首轮的 20 张边界不符涉及版本/布局差异，不能因为名字一样就认定结构相同。本轮对其中 15 张得到伴生布局候选，仍非目标变体原生实现证明；另外 5 张继续拒绝，见[平面候选索引](<../derived/config-layout-recovery/layout-index.json>)。

## 4. ARM64 静态核对门槛

顺序读取器声明可查 [PbReadBuf:140575–140646](<../derived/il2cpp/arm64-v8a/dump.cs#L140575-L140646>)；例如 `readUInt32(out uint dest)` 地址为 `0x21f6908`。同名但另带 `int pos` 的随机位置读取器有不同地址，必须排除，不能只比较方法名。

[解码脚本](<../tools/decode_resbin.py>) 的当前保守门槛是：

- 从 ELF 的 PT_LOAD 映射 RVA/VA 到文件字节，不把虚拟地址直接当文件偏移。
- 仅在当前方法范围内做有限指令识别；上限 16 KiB，达到上限则拒绝。处理直接 BL、B-tail、条件分支、RET/BR/BLR。
- MOV/ADD 跟踪 `self`、入口 buffer 和对象字段偏移；条件汇合只保留各路径一致的事实；不跟踪栈溢出/恢复的 provenance。
- 调用按 AAPCS64 假设清除易失寄存器及 LR；保守丢弃未知写入、load/store pre/post-index 写回基址；不混淆 XZR 和 SP。
- 局部 CFG 不得有环；按地址排列的每个 reader 节点必须支配下一个 reader 节点。不能只把互斥分支上的调用地址拼成一串。
- 每个读取调用的 X0 必须仍来自入口 buffer、偏移 0；X1 必须为 `self + metadata 字段偏移`。
- 调用目标必须对应**顺序重载**，reader 类型顺序必须与全部字段顺序吻合。

这是受限的静态证据筛选器，**不是通用反编译器或反序列化程序等价性证明**。未独立证明所有被调函数遵守 ABI，未知调用仍可能修改 buffer/游标；支配链也不证明所有返回成功的路径都消费全部字段。每个输出的 `unpack_reader_calls` 和 `native_analysis_checks` 保留这些核对结果，便于人工复查。

## 5. 载荷接受模型与数值精度

支持 `byte/short/ushort/int/uint/long/ulong/float/string/FP`，数值按大端模型读取。字符串采用大端 int32 字节长度、长度包含末尾 NUL、严格 UTF-8；长度范围 1…1,000,000 是**工具接受策略**。

首轮将大端作为受限接受模型；本轮另从构造/reset 指令确认 `IsNetEndian=1`，并核对整型 `NetworkToHostOrder` 调用，见[扩展报告第 4 节](<核心配置扩展解码.md>)。**按一种端序读再按同样端序写回本来也可能一致，因此回编码本身仍不是端序或业务语义证明。**

新增递归解码已将每个 `readString` 调用的 native `maxStrSize` 纳入 schema，并遵循更小上限。原生读取器解码 `length-1` 字节后前进 length，并未明确检查保留字节为零；工具仍额外要求末尾 NUL 与严格 UTF-8，是保守接受子集，不是完整容错语义复现。

首轮标量解码器的 FP 只输出 `字段名__raw_int64`。本轮已从读取器和算术实现恢复 signed Q32.32 表示，扩展输出另有精确十进制镜像；但数值表示不等于字段业务单位，**不将所有字段自动解释为百分比、秒数或实际倍率**。详见[扩展解码报告](<核心配置扩展解码.md>)及[算法报告](<客户端玩法算法还原.md>)。

64 位整数在 Python 中可精确保留；JavaScript Number 超过 `2^53`、Excel 自动数字列可能丢精度。请用 Python 整数，或将这些列按文本导入；不要经过 GUI 数字转换再覆盖原始数据。

## 6. 一个能追到原字节的样例

[BattleCore.LongHunSkillConfig JSON](<../derived/config-decoded/BattleCore/LongHunSkillConfig.json>) / [CSV](<../derived/config-decoded/BattleCore/LongHunSkillConfig.csv>)：

- `unpack` RVA `0x1643a0c`；四个 uint 字段，metadata 对象偏移 16、20、24、28。
- 前三个 reader 为 BL，最后一个是 B-tail `0x1643ac8` → `0x21f6908`；只抓 BL 会漏掉最后一项。
- 原载荷第一条从字节偏移 20 起，占 16 字节，候选值为 `SkillID=1, SkillLv=0, ActiveSkillID=0, SkillCoolTime=10`。
- 全表 105 条。这里只保留 `SkillCoolTime=10` 的原始字段值，未宣称它等于 10 秒。

[ResDef.LevelBaseConfig CSV](<../derived/config-decoded/ResDef/LevelBaseConfig.csv>) 每条 63 字节，第一条起点 20，第二条起点 83；而 [BattleCore 同名表 CSV](<../derived/config-decoded/BattleCore/LevelBaseConfig.csv>) 每条 46 字节。两者都是 5,268 条，但不是同一个布局。

## 7. 输出与验证

每个 JSON 记录含 `_record_index`、`_byte_offset`、`_byte_length`；`source` 记录 Bundle、path ID、原字节 SHA-256、schema、字段对象偏移和读取器地址。CSV 用于浏览，JSON 是保留原始字符串/整数的权威分析副本。

CSV 的公式样式字符串（忽略前导空白后以 `= + - @` 开头）加单引号前缀；当前共 4 个单元格。该差异有意保留并由验证脚本核对，不修改原始 TextAsset 或 JSON。

[输出验证器](<../tools/validate_outputs.py>) 检查：

- 655 个 TextAsset 的大小与哈希；545 个 resbin 的头、长度和反相 CRC。
- 每张成功表的记录数、字段对象偏移、记录起点和长度。
- 280 张表、108,533 条记录从 JSON 重新编码后，与**完整原载荷逐字节相同**。
- CSV 的记录数和安全转义后值；首轮标量目录没有未索引旧表。新增递归目录为保留历史证据，另留有 24 个明确标注 `UNINDEXED-stale` 的旧 JSON/CSV，**不是当前有效交付表**；清单和哈希见[扩展输出审计](<../derived/config-extended/output-validation.json>)，只按当前索引读取。
- 1 个正向标量/UTF-8/FP 样例，以及截断、尾部数据、负长度、零长度、缺 NUL、非法 UTF-8 六个拒绝样例。

当前结果见 [输出校验](<../inventory/output-validation.json>)。这些检查验证归档数据结构和转换一致性，不证明服务端规则或游戏动态行为。
