## 3. 不是“照元数据顺序猜布局 + roundtrip”

### 3.1 固定数组没有序列化 count 前缀

`count_encoding=none-native-fixed` 表示从 native 指令恢复固定读取次数，**不读取 wire 上不存在的 count**。托管数组的 `+0x18` 长度加载仅用于对象边界检查，不能误认为 payload count。

例如 [ResDef.BootyConfig 指令](<D:/VibeCoding/勇者养成记/本地分析/derived/config-extended/native/ResDef.BootyConfig.asm.txt>)：

```text
0x1dca254  mov x21, #-1
0x1dca258  mov w22, #0x20
0x1dca25c  ...                 ; 循环体
            ... add x1,array,x22 ; native 数组目标地址
            ... bl readInt32    ; 原始 buffer receiver
0x1dca2ac  add x21,x21,#1
0x1dca2b0  cmp x21,#2
0x1dca2b4  add x22,x22,#4
0x1dca2b8  b.lt 0x1dca25c
```

初始 -1、读取后递增、比较 2，产生 **3 次**读入；目标从数组对象 `+0x20` 开始，以 4 字节步进。不是从最大字段值、表尾对齐或重编码反推。

其他优先循环的原始证据：

| schema / 字段 | 初始 / 比较 / 回边 | native 得到的次数 |
|---|---|---:|
| ResDef.EquipConfig / ImpactData | `x23=0`；`0x1dd45dc cmp x23,#3` 后加 1；回边 `0x1dd45e4` | 4 |
| ResDef.EquipConfig / OpenHoleList | `x22=0`；`0x1dd46f4 cmp x22,#5` 后加 1；回边 `0x1dd46fc` | 6 |
| ResDef.EquipUpLevelConfig / ImpactData | `x23=0`；`0x1dd6208 cmp x23,#2` 后加 1；回边 `0x1dd6210` | 3 |
| ResDef.SkillBaseConfg / AttrDamageData | `x22=0`；`0x1e93f78 cmp x22,#1` 后加 1；回边 `0x1e93f80` | 2 |
| ResDef.SkillBaseConfg / BuffID | `x21=-1`；读取后加 1 再 `0x1e93fe0 cmp x21,#3`；回边 `0x1e93fe8` | 4 |

**比较与递增的先后顺序不同，不能只做“比较立即数 +1”。** 每个 schema 的 `native_evidence.loops` 保留完整循环体、邻近前导指令、更新/比较指令、机器码字节及有序的 concrete branch tests，末次条件必须不跳转。另有无回边的 singleton 数组；例如 ElfHelpConfig 只读元素 0，并明确记录 nonempty/bounds 成功路径假设。

参考：[EquipConfig schema 证据](<D:/VibeCoding/勇者养成记/本地分析/derived/config-extended/schemas/ResDef.EquipConfig.json>)、[SkillBaseConfg schema 证据](<D:/VibeCoding/勇者养成记/本地分析/derived/config-extended/schemas/ResDef.SkillBaseConfg.json>)、[BattleCore.SkillBaseConfg schema 证据](<D:/VibeCoding/勇者养成记/本地分析/derived/config-extended/schemas/BattleCore.SkillBaseConfg.json>)。

### 3.2 嵌套目标、callee、buffer 必须同时对应

静态模型逐条追踪 ARM64 寄存器及显式栈保存，要求：

1. sequential reader 的 `x0` 为原始 `PbReadBuf`，`x1` 为准确对象字段地址或连续数组元素地址。
2. nested unpack 的 `x0` 来自准确 nested 字段或元素，`x1` 为原始 buffer，`x2=1`。
3. 实际直接调用目标与 metadata 中声明的嵌套 schema 完全一致；继续递归校验嵌套方法。
4. scalar 一次、array 的目标连续且 stride 正确；实际消费顺序必须与声明字段逐一对应；剩余/遗漏/歧义事件拒绝。
5. 按 AAPCS64 清除调用者保存寄存器；未知调用、未支持指令/操作数模式、无法确定的数据依赖分支均拒绝。

例如 [ResDef.ResAttrImpactData](<D:/VibeCoding/勇者养成记/本地分析/derived/config-extended/schemas/ResDef.ResAttrImpactData.json>) 保留真实字段名 `DataType` / `AddType` / `Value`，native reader 是 `readInt16` / `readUInt8` / `readFloat`；wire 长度为 7 字节，不能照 IL2CPP 对象对齐填充。BattleCore 对应结构的 FP 值使用 `readInt64`，不可与前者混同。

### 3.3 审计后新增 fail-closed 防护

独立审阅通过内存中的指令突变发现两个模型漏洞；它们不是当前真实方法已损坏的证据，但确实能使错误候选被接受。现均已修正并回归：

- 在 `0x1e8947c` 将 `MOV X19,X1` 改成 `MOV W19,W1`：以前指针 token 穿过 32 位截断；现在 W 寄存器**读和写**都拒绝符号指针截断。仅允许明确建模的 uint32 数组长度和不超过 32 位的 scalar read result。
- 在 `0x1e89498` 注入 `STR XZR,[X19,#0x10]`：以前忽略对 buffer 对象的破坏；现在拒绝 buffer/global/未知区域/未证明对象写入。指令 store 只允许显式栈保存，或精确宽度、已证明源自栈 temporary 的 read-result→self 链。
- 保存并核对 native memory 读写宽度；重叠写使旧符号值整体失效，避免部分写后“复活”旧指针；整数寄存器和 store 遵守实际位宽截断。未建模的扩展/移位/寻址及 `ldrsw` 保守拒绝。

这不是对任意 ARM64 方法的形式化验证器；它是仅接受已建模模式的受限静态成功路径分析器。

### 3.4 来源身份与输出路径碰撞修复

父代理的完整来源校验发现真实集成问题：non-FP 与 FP 的 CiTieFuncConfig 都映射到同一个 BattleCore schema，旧版输出只以 `(namespace,type)` 命名，导致后写源覆盖前写源。即使两个 payload 字节完全相同、都能 roundtrip，**bundle/path_id 来源仍不相同**，不能把它们合并为同一份来源元数据。初版全量 byte/row 验证没有检查这一项，现已补齐。

现于任何写入前对全部 174 个 target 规划源身份 `(bundle,path_id,sha256)`：非冲突类型保留既有路径；同 namespace/type 的来源统一添加稳定 `__source_<来源身份 SHA256 前16位>` 后缀。若摘要路径仍冲突，或源身份重复，直接停止而不继续写入。全部写入后再次检查 JSON/CSV 路径全局唯一，并要求**每一张 JSON 的完整 `source` 与相应 index entry 完全相等**，而非只比对 hash。

共 12 个 schema 名碰撞组、24 个目标来源，其中 10 项 payload 拒绝，14 个成功输出采用来源后缀；其他成功输出路径不变。实际非 FP / FP CiTieFuncConfig 分别为 [non-FP 来源](<D:/VibeCoding/勇者养成记/本地分析/derived/config-extended/BattleCore/CiTieFuncConfig__source_1f3e47d9b98ac6c9.json>) / [FP 来源](<D:/VibeCoding/勇者养成记/本地分析/derived/config-extended/BattleCore/CiTieFuncConfig__source_e5323f2a6acaf81d.json>)。

**旧版无后缀的碰撞文件未删除，属于未索引的 legacy-stale 产物，不是当前交付。** 只能依据当前逐表索引枚举有效表，不能把目录 glob 的全部 JSON 自动认作当前结果。碰撞组中任一来源没有通过 payload 校验，也不得将另一来源输出当作它的结果。

## 4. Reader、格式与精度

### 原始 reader 证据

[默认构造](<D:/VibeCoding/勇者养成记/本地分析/derived/config-extended/native/PbReadBuf.constructor_default.asm.txt>)、[buffer 构造](<D:/VibeCoding/勇者养成记/本地分析/derived/config-extended/native/PbReadBuf.constructor_buffer.asm.txt>)、[reset](<D:/VibeCoding/勇者养成记/本地分析/derived/config-extended/native/PbReadBuf.set_buffer.asm.txt>) 将 `IsNetEndian` 字节设为 1；[readInt32](<D:/VibeCoding/勇者养成记/本地分析/derived/config-extended/native/PbReadBuf.readInt32.asm.txt>) 在 `0x21f68dc` 调用 `NetworkToHostOrder`，[readInt64](<D:/VibeCoding/勇者养成记/本地分析/derived/config-extended/native/PbReadBuf.readInt64.asm.txt>) 在 `0x21f6a44` 做对应转换。

- Header 为 big-endian `>5I`：tag `0x2def`、总长度、版本 1、记录数、payload 的 `zlib.crc32(payload) ^ 0xffffffff`。
- 数值 reader 使用真实调用确定的宽度/符号/float32；不依据 enum underlying storage 或对象字段 offset 猜 wire 宽度。
- [readString](<D:/VibeCoding/勇者养成记/本地分析/derived/config-extended/native/PbReadBuf.readString.asm.txt>) 先读有符号 int32 长度，要求 `0<length<=maxStrSize`，UTF-8 解码 `length-1` 字节，再前进完整 length。每个调用的 native `maxStrSize` 都进入 schema。
- **native 并未明确检查最后保留字节为零**。本解码器额外要求末字节 NUL、严格 UTF-8；这是有意的保守子集，不能声称完全复现 native 字符串容错语义。

### FP / int64 / uint64

JSON 保留精确整数 number token；所有 FP/long/ulong 字段同时增加 `__decimal` 字符串镜像；FP 字段名增加 `__raw_int64`，保留**原始有符号 int64**，不推测缩放系数。数组同时保留元素逐一对应的 decimal 字符串数组。源资产 `path_id` 也有 `path_id_decimal` 镜像。

Python 等任意精度 JSON parser 可读取 number；JavaScript/Excel 使用者必须读取 decimal 镜像或采用 lossless JSON parser，不能先经普通 JS Number 再转换。

CSV 使用标准 quoting、UTF-8 BOM；嵌套值为 compact JSON。公式前缀（含前导空白/BOM/控制字符）加 apostrophe 防护；超过 JS 安全整数范围的整数及数字字符串同样文本化，防止表格自动转换损失精度。JSON 不做这些展示层转义，始终保留源字符串和值。
